1. Why This Project Exists
1.1 The real-world problem
Modern backend systems are built as microservices : a single user request (search a hotel, post a
payment, load a timeline) is broken into a chain of internal calls across many small, independently-
deployed services. When any one service in that chain gets overloaded, the slowdown propagates
backward through every service waiting on it ΓÇö wasting all the work already completed earlier in the
request path, and dragging otherwise-healthy services down with it. This is cascading overload ,
and it is one of the most common ways large backend systems degrade under real tra∩¼Çic spikes.
Concrete, verified scale numbers (from Rajomon, NSDI ΓÇÖ25 ΓÇö the paper this project extends,
verified directly against the paperΓÇÖs own text and o∩¼Çicial USENIX abstract):
ΓÇó Evaluated at up to 140 CPU cores across CloudLab servers, under bursts up to 30,000
requests/second .
ΓÇó Prior state-of-the-art overload-control baselines (T opF ull) take up to 10 seconds to react
to a load spike, and multiple baselines take several seconds to recover after one ΓÇö versus
RajomonΓÇÖs sub-second reaction and recovery .
ΓÇó RajomonΓÇÖs own headline result: 78% lower tail latency , 45% higher goodput than prior
state-of-the-art overload control, in high-load scenarios.
The gap this project targets: RajomonΓÇÖs entire mechanism ΓÇö a decentralized, market-like
system where requests carry ΓÇ£tokensΓÇ¥ and services set congestion-based ΓÇ£prices,ΓÇ¥ with no central
coordinator ΓÇö is implemented and evaluated specifical ly for gRPC , using gRPCΓÇÖs native interceptor
and metadata system to attach this information to every call. REST/HTTP ΓÇö which remains the
default way most public-facing APIs and a large share of internal service boundaries communicate,
and the protocol spoken by the API gateways (Envoy , NGINX) that front a huge share of real
production tra∩¼Çic ΓÇö has no equivalent built-in mechanism. There is currently no working, evaluated
version of RajomonΓÇÖs mechanism for REST/HTTP systems. This project builds and evaluates one.
1.2 Project name
W orking title: Rajomon-HTTP . The name is deliberately a portmanteau, following the same
convention as the paperΓÇÖs own naming of its point of comparison (ΓÇ£T opF ullΓÇ¥ as a name for its
own mechanism) ΓÇö it keeps ΓÇ£RajomonΓÇ¥ for direct lineage/attribution to the base mechanism being
extended, and appends ΓÇ£HTTPΓÇ¥ to name the one axis being changed. This is a working title ,
explicitly open to revision as the project develops; nothing about the technical design depends on
the name.
1.3 Scope ΓÇö which real-world stages this project touches
Rajomon-HTTP is a research/systems extension project, not a production system, so ΓÇ£scopeΓÇ¥ here
means: which parts of a full overload-control deployment does this project actually build and
evaluate, versus reason about but not implement.

1.4 What must be dynamic / config-driven, with no advance knowledge
ΓÇó Per-service price computation must not be hardcoded. The system has no advance
knowledge of which service will become congested, when, or by how much. Price must be
computed live, per service, from that serviceΓÇÖs own local congestion signal at request time ΓÇö
never a fixed or pre-scripted value.
ΓÇó The set of services and their call graph must not be assumed fixed at build time.
The middleware/sidecar logic must work by intercepting whatever request/response passes
through it, without embedding assumptions about a specific fixed topology , so it can be
pointed at any service in the benchmark app without per-service custom code.
ΓÇó T oken budgets must be a request-time parameter, not a constant baked into the
client. The evaluation harness must be able to vary starting token budgets without code
changes, since sensitivity to this parameter is part of what an evaluation would want to
explore.

3. Cross-Cutting Requirement: T ransparent, Zero-Application-
Code Integration
3.1 What it is and why itΓÇÖs central
The single non-negotiable property carried over from the base paper is that overload control must
be completely transparent to the application code it protects . The original Rajomon
works purely as a gRPC interceptor ΓÇö the Hotel Reservation and Social Network application code
inside each service is never modified. Rajomon-HTTP must preserve this property for REST: the
benchmark applicationΓÇÖs own code is never touched. All logic lives in the sidecar, sitting
outside the service.
3.2 How itΓÇÖs implemented
ΓÇó The sidecar is deployed as a separate container/process in front of each service (see Section
8, System Architecture), not as a code change inside the service.
ΓÇó Communication between the sidecar and the service it protects happens over localhost HTTP ,
with the sidecar acting as a local reverse proxy ΓÇö the service never knows the sidecar exists.
ΓÇó T oggling Rajomon-HTTP on/off is a deployment-level decision (whether the sidecar con-
tainer is present in front of a given service), not a code-level flag inside the application.
3.3 What is and isnΓÇÖt covered by this guarantee
ΓÇó Covered: the benchmark applicationΓÇÖs business logic (Social NetworkΓÇÖs post/timeline/user
services) ΓÇö zero modification.
ΓÇó Not covered: the gateway configuration itself. Envoy/NGINX does need configuration
changes (routing rules, and potentially explicit allow-listing of the custom headers) ΓÇö this
is infrastructure configuration, not application code, but itΓÇÖs worth being precise that ΓÇ£zero-
touchΓÇ¥ applies to the application , not to every piece of infrastructure in the path.
3.4 Interview talking point
ΓÇ£The design goal we inherited from the base paper is that overload control has to be something
you can bolt onto an existing system without rewriting it ΓÇö thatΓÇÖs what makes an idea like this
practical ly adoptable, not just a research toy. W e kept that property in our REST port by keeping
every piece of Rajomon-HTTPΓÇÖs logic in an external sidecar container, so the actual benchmark
application code is never touched. The tradeoff is that infrastructure config ΓÇö the gateway ΓÇö does
need to cooperate, which is exactly the risk we test for directly in our evaluation. ΓÇ¥

ΓÇó rajomon_request_total (per-sidecar decision) is kept separate from request_outcome_total

itself cause this outcome, or something else downstream?ΓÇ¥ ΓÇö exactly the kind of question a

7.2 Key flows, arrow notation
Normal (admitted) request flow: Client -> Gateway -> Sidecar A [tokens >= price:
OK] -> Service A -> Sidecar A [attach price] -> Sidecar B [tokens >= price: OK]

8. Core Logic ΓÇö The Admission Engine
8.1 Determinism
The admission decision (forward vs. reject) is deterministic given its inputs ΓÇö tokens remaining
and current local price ΓÇö in the sense that the same (tokens, price) pair always yields the same
admission outcome. This matters for the same reason it matters in the base paper: a load-shedding
mechanism whose behavior canΓÇÖt be reasoned about or reproduced is very hard to trust or debug in
production. What is not deterministic, by design, is the price itself over time (itΓÇÖs a live function
of real, changing load) and the token amount attached per request (randomized per Decision-
derived design, mirroring the base paperΓÇÖs ΓÇ£randomized token spending,ΓÇ¥ Section 7, Slide 7 of the
presentation) ΓÇö those are intentionally variable; the decision rule applied to them is not.
8.2 Every distinct rule/case, pseudocode-style
function on_incoming_request(request):
tokens = read_header(request, "X-Rajomon-Tokens")
price = get_local_price() # computed from this service's own live load
if tokens is MISSING or MALFORMED:
# Golden rule: fail OPEN, never fail closed (Decision #7, Section 4)
forward(request, attach_price=price)
return
if tokens >= price:
remaining = tokens - price
set_header(request, "X-Rajomon-Tokens", remaining)
forward(request)
# on the way back:
set_header(response, "X-Rajomon-Price", price)
return response
else: # tokens < price
return HTTP_503(reason="insufficient tokens for current price")
function get_local_price():
congestion_signal = observe_local_load() # e.g. queue depth / recent latency
price = price_function(congestion_signal) # monotonically increasing in congestion
return price
8.3 The golden rule / safety default
When in doubt, let the request through. Any ambiguous, malformed, or missing-header
situation resolves to fail-open (forward the request as if Rajomon-HTTP werenΓÇÖt present), never
fail-closed. A bug in the overload-control layer must never become a new outage. This is stated
once here and is the single most important safety property of the whole system ΓÇö everything else
is an optimization on top of this default.

13. Interview T alking Points
On the core idea:
1.ΓÇ£The one-sentence version: every service prices itself based on its own live congestion, and
that price rides back to the client on the response, so the whole system self-regulates without
anyone needing a global view of it. ΓÇ¥
2.ΓÇ£What makes this decentralized-and-coordinated combination hard is that those two properties
usual ly trade off against each other ΓÇö decentralized systems typical ly lack the information to
coordinate wel l, and coordinated systems typical ly need some central point with a global view.
The trick is that the coordination information isn ΓÇÖt sent through a separate channel ΓÇö it rides
on network tra∩¼Çic that was going to be sent anyway. ΓÇ¥
On why this project (the extension) is more than a relabeling exercise:
3.ΓÇ£gRPC gives you a built-in, guaranteed metadata channel for free. HTTP doesn ΓÇÖt ΓÇö the
closest equivalent is a custom header, and headers aren ΓÇÖt guaranteed to survive the trip. Real
gateways routinely strip headers they don ΓÇÖt recognize, which means a naive port could silently
stop working and youΓÇÖd have no idea. ThatΓÇÖs a genuine systems problem, and itΓÇÖs specifical ly
what our header-survival test is built to catch. ΓÇ¥
4.ΓÇ£W e deliberately scoped our evaluation to include a real gateway in the loop, not just a direct
service-to-service test ΓÇö because skipping that would mean we hadn ΓÇÖt actual ly tested the thing
that makes this port risky in the first place. ΓÇ¥
On architecture:
5.ΓÇ£Every piece of our logic lives in an external sidecar container, never inside the benchmark
application ΓÇÖs own code ΓÇö that was a hard requirement, because the whole value proposition of

6.ΓÇ£The sidecar only ever touches headers, never the request or response body ΓÇö thatΓÇÖs a deliberate

On the admission logic:
7.ΓÇ£The actual decision rule is dead simple and deterministic ΓÇö do the tokens on this request
