2. How This Should Actually Be Built
This is not a tutorial. It is written the way an engineer keeps their own build notes: build one
verifiable layer, prove it works, only then build the next layer on top of it. There is no deadline
pressure here ΓÇô this project is for learning, not just completion, so questions along the way are
expected and welcome, at any phase.
2.1 Core principle: never build on unverified ground
Every phase below has an Entry Condition (what must already be true and already verified)
and an Exit Condition (a literal checklist you run and confirm before moving on). A bug caught
the moment itΓÇÖs introduced costs minutes. The same bug caught three phases later ΓÇô after the
admission engine, the metrics pipeline, and the load tests are all built on top of it ΓÇô costs hours,
and itΓÇÖs often unclear which layer is actually at fault. Do not skip an exit-condition check because
ΓÇ£itΓÇÖll probably work. ΓÇ¥
2.2 Git discipline
One commit per phase. Exact commit message format:
[Phase N] <Phase Name> -- <one-line summary of what now works>
Example: [Phase 3] Admission Engine -- token/price decision logic live on compose-post-service
Do not squash multiple phases into one commit, and do not commit mid-phase with a message
describing a different phaseΓÇÖs work.
2.3 Infrastructure rule (holds for the whole project)
Everything runs in Docker. Nothing is installed natively on the host , including Go itself,
Envoy , Prometheus, or Grafana. If a phase needs a Go toolchain to build the sidecar, that build
happens inside a Docker multi-stage build ( docker build ) or viadocker compose run , never via
a locally-installed go binary . This guarantees the project is reproducible on either teammateΓÇÖs
laptop without a ΓÇ£works on my machineΓÇ¥ gap, and it matches the projectΓÇÖs own stated evaluation-
reproducibility goal (Context Document, Section 5.5-5.6).
2.4 Env var discipline
ΓÇó A committed .env.example file lists every environment variable the system uses, with a
placeholder or safe default value and a one-line comment.
ΓÇó An actual .env file (gitignored, never committed) holds real local values.
ΓÇó Note specific to this project: unlike a typical web app, Rajomon-HTTP has no external
API keys or user secrets to protect ΓÇô there is no third-party service being called. The env var
discipline here exists for a different reason: it keeps tunable system parameters (base price,
price scale factor, default token budget, listen ports) out of hardcoded source code, so they
can be changed per-experiment without recompiling. T reat .env as experiment configuration,
not secret storage, but keep the same discipline regardless.

2.5 The phase-chat rule
Each phaseΓÇÖs chat builds only what is specified for that phase. If, while building, you notice
something that seems like it should be different in an earlier phaseΓÇÖs already-committed code, do
not silently change it . Stop, state the concern explicitly (what you noticed, why it seems like a
problem, what changing it would affect), and get a decision before touching already-verified code.
Do not jump ahead and start building a later phaseΓÇÖs files early , even if it seems convenient in the
moment ΓÇô later phases assume the exit conditions of every earlier phase are true, not ΓÇ£mostly true. ΓÇ¥
2.6 What this guide adapted out, and why
This template was originally written for a full-stack web application. Rajomon-HTTP is a sys-
tems/networking research project with no end users, so the following concepts from a typical phase
guide do not apply and are intentionally not separate phases here:
ΓÇó User authentication / accounts / roles-based login ΓÇô there are no human end users
of this system; the ΓÇ£actorsΓÇ¥ are Client, Gateway , Service, and Sidecar (Context Document,
Section 2), not people with logins.
ΓÇó A background job queue (e.g. Celery/Redis workers) ΓÇô the sidecar handles each
request synchronously , inline, as a reverse proxy; there is no asynchronous task processing in
this system.
ΓÇó A custom frontend ΓÇô there is no hand-built UI. Its role is filled by Grafana dashboards,
folded into Phase 6 below.
ΓÇó Data ingestion pipelines ΓÇô the closest equivalent is deploying the benchmark application
and generating synthetic load, which is covered in Phases 1 and 6.

Phase 5: Gateway & Header-Survival T est
Phase Goal
At the end of this phase, an Envoy gateway sits in front of the whole system, and the single
biggest open risk in this entire project (Context Document, Sections 1.1, 4 Decision #6, and
Slide 9 of the presentation) has been empirically tested and documented , either way: does
